# benchmarks_balanced 结果分析

> 日志迁移更新：原日志现已转换为共享 pipeline 的结构，并按首次已有 Equivalent=true 截断。本文及原指标文件仍是迁移前快照；迁移与备份见 [说明](../../benchmark_log_migrations/migration_summary_zh.md)。

> 后续更新：std 原日志已补入离线 oracle 结果，见 [std 补算结果](std_oracle_backfill_summary_zh.md)。下文及原 CSV/JSON 为补算前的分析快照，其中“std 未运行 oracle”描述历史运行；新增的自然语言 judge 仍待补算。

分析日期：2026-11-10。范围：logs/benchmarks_balanced 中的 gpt-oss、icl_gen、reg 实验。

## 核心结论

**本轮 68 个 setting 的 std/CE 共 136 份预期日志均已生成，每个只有 1 个 run。** 已与默认 balanced 清单逐项核对，无缺项、无额外任务；记录合计 673 个 epoch，其中 670 次规则生成，另有不生成新候选的终止记录。此次没有发现 cvc5 缺失或其他顶层 oracle 异常。日志齐全不等于全部任务成功。

可以看到真实的 CE 纠错收益，尤其是 SCAN length/addprim_jump 与列表 c164。但整体结论仍受 Python 执行子集、单次采样、std/CE 不同预算、有限评测，以及一个新发现的**列表输入原地修改污染问题**影响。不能仅用一个汇总成功率判断方法优劣。

## 统计口径

- “最后一条记录”如实反映日志结尾；它可能是无效输出，也可能是没有评分的终止标记。
- “最后一次可评分候选”是按时间取最后一条带数值 scoreEvalSet 的候选，不是挑选测试集最高分。后续无效输出通常不会更新 runner 的 previous，因此该口径有助于观察保留的有效候选。
- “曾经达到”取整个轨迹的最高记录，只用于说明生成过什么，不视为可部署的模型选择策略。
- null 表示未评分/未证明，绝不直接当作语义准确率 0；“满分任务数”始终以所有 setting 为分母，未评分单列。
- List 的测试集每个只有 10 条；SCAN 的 scoreEvalSet 只检查测试 split 的前 32 条。SCAN CE 的 Equivalent=true 另由完整公开 20,910 条命令枚举检查。List 无反例返回 null，不会证明全域等价。
- Instruction Induction 的 Equivalent 来自 LLM judge，不是可执行程序的形式验证；该任务没有执行准确率。

## 2. Cryptography：依赖修复有效，主要体现提前停止

12 个实例覆盖 Caesar、Atbash、keyboard 三族，各 4 个。两种方法所有测试均满分，CE 每题第一轮就通过等价检查。

- std：共 36 次规则生成，通常 N=3、6、10；虽然第一轮已正确，仍按样本计划继续。
- CE：共 12 次规则生成，每题 N=8 即停止。
- 因此这里的主要收益是 oracle 证明后提前结束，不能解释为通过反例学习出更复杂的规则。
- 未再出现上轮的 CLI 缺失；说明本轮日志中的 solver 路径已正常工作。

### 有实际 CE 作用的两条轨迹

**addprim_jump：** epoch 0 因签名不符合 transform(x) 被拒绝；epoch 1 在原 8 条数据上生成可执行但错误的候选，测试准确率 9.375%；epoch 2 加入 8 条真正被旧候选判错的命令，N=16 后达到测试 100%，且完整命令域等价。这里确实存在“错误候选 → 新反例 → 正确解释器”的链条。

**length：** 测试轨迹为 epoch 0: 0%，epoch 1: 校验失败，epoch 2: 0%，epoch 3: 6.25%，epoch 4: 71.875%，epoch 5: 无 ans，epoch 6: 71.875%，epoch 7: 100% 且完整域通过。累计 N 从 8 增长到 28。新反例涉及 opposite/around、twice/thrice、turn 与 after 的组合。例如反复出现 turn around right thrice after run opposite right twice，要求先执行两次 run-opposite-right，再执行 12 次右转。轨迹有明显进步，也有无效输出和重复反例。

离线复核了这两题所有有 previous 的 CE batch：8 个 batch、64 条记录都确实是旧候选的错误输入。它们不一定都是新字符串；N 在一些轮次不增长，表示系统仍在反馈已见过但未解决的错误。

### 另两条成功主要来自相同 prompt 的再次生成

template_jump_around_right 与 template_opposite_right 都在 epoch 0 校验失败、epoch 1 成功，N 始终为 8。两轮 Prompt 逐字符相同，没有新增反例或跨 epoch 的失败反馈。这两题的成功不能归因于新的 CE；应与上面两条真正的反例迭代分开。

### 失败仍然大量来自输出/校验契约

SCAN std 的 64 次生成有 47 次 attempt error；CE 的 47 次生成有 37 次。除 import/while/nonlocal 和不允许的方法外，还出现大量 Expected transform(x)。**需要且可以修复的输入签名契约仍是主要障碍。** 本轮分析不自动放宽 validator，也不执行被其拒绝的程序。

simple 与 template_around_right 的 std 都曾达到 32 条测试满分，后续又生成无效输出；所以“最后记录只成功 1/8”并不等同于“仅一个 split 曾学会”。反过来，32 条满分也不能声称覆盖完整语法域。

## 4. List Functions：有局部纠错收益，也有无限补样本和数据污染

### 代表性收益：c164

参考函数对每个 n 返回 n // 4 + 5。CE 第一候选是复杂的素数计数加样例特殊处理，测试 0%；加入一批真实反例后，epoch 1 直接改成 return [n // 4 + 5 for n in x]，测试 100% 并保持。

实际反例：输入 [51, 27, 33, 11, 59, 21, 0, 22]，正确输出 [17, 11, 13, 7, 19, 10, 5, 10]；旧候选输出 [19, 11, 13, 7, 21, 11, 4, 11]。Std 此题唯一可评分候选为 0%，后续被语法限制拒绝。这是很适合继续做 reasoning trajectory 分析的个案。

### c211：测试满分仍然有反例

参考函数先反转，再做两次插入。Std 三轮测试都为 60%；CE 从 50% → 80% → 100%，最后保持测试满分。

但 CE 最后一轮 Equivalent=false，说明 oracle 仍找到反例。模型主要用奇偶长度、中心位置、mod 4 分支解释数据，不能据 10 条测试满分认定已经恢复参考程序。例：输入 [81, 43, 23, 99, 24, 10] 的正确输出为 [10, 24, 99, 23, 23, 23, 43, 81]，第一候选在插入位置上仍错误。这反映出 CE 可以改善样本外行为，但也可能走向越来越复杂的近似规则。

### 无反例时仍持续追加普通数据

离线按实际 prompt 中的 previous 检查了 142 个列表追加 batch、1,135 条记录：按保存的数据，176 条被旧候选判错，959 条已被正确预测。也就是说约 84.5% 属于普通补充数据。**该计数还包含 c067 的污染，不能把全部 176 条都称为有效反例。**

剔除 c067 后，有 136 条记录（17 个 batch）确实揭示先前候选的错误；其他已正确记录仍很多。多道简单题第一轮已经满分，却一直补到 N=64、跑满 8 轮。原因仍是 List oracle 无反例只返回 null，runner 接着 fallback 补样本。这解释了为何 CE 列表共 189 次生成，远高于 std 的 72 次。

### 新发现：c067 的原地修改污染了 CE 数据与评分

参考函数 c067 会直接交换 x[0] 和 x[-1]，再返回同一个 x。当前 reference_output(x) 直接把数据池中的原对象交给它，而没有复制。由此有两个后果：

- 生成反例时，池中的输入已经被参考函数修改；返回的期望输出与修改后的输入还是同一个列表，保存的 pair 变成“输入等于输出”。
- 池中还包含 self.train 和 self.eval 的输入对象，因此 oracle 调用可以改变后续评测所使用的输入，成绩不再对应原始数据集。日志中的已有 pair 也可能通过共享引用被后续修改。

具体复现：x=[1,2,3] 调用 reference_output(x) 后，x 和返回值都变成 [3,2,1]，且二者是同一对象。

本次将每条记录中的输入先 deepcopy，再执行参考函数核对标签：**c067 保存的 64 条 CE 记录全部与目标 swap 映射不符**（包括多轮重复）；其余抽查范围是所有已保存的 List CE 条目，未发现其他 ID 的标签不符。示例：[61,63,87] 被标成 [61,63,87]，实际 swap 应为 [87,63,61]。CE 最终仍输出正确的 swap 程序，却只记成 40%，因此不能把此题的 std 100% vs CE 40% 当作学习退步。

此外 predict(candidate,x) 也直接把原对象交给模型程序；允许的原地操作可能污染数据。这是需要优先修复并重跑受影响题目的适配器 bug。本次只分析，没有修改执行路径。

### 另一个终止记录陷阱：c124

c124 的目标是 [x[x[0]]]，在大量随机 0–100 输入上可能越界。CE 从 20% 修正到测试 100%，但最终追加数据找不到可用新输入，写入 NoCounterexample=true、Equivalent=null 的终止记录，未复制前一轮 score。直接读最后一条会把它当成无分数；应保留“最后可评分候选满分”与“未作全域证明”的区别。

## 5. Instruction Induction：19/24 被 judge 接受，但不能当作准确率

CE 的 24 题最终有 19 个 true、4 个 false、1 个 null。14 题只生成一次就被接受；其余成功题包括 cause_and_effect、rhymes、singular_to_plural、num_to_verbal、informal_to_formal 等。

- 最终 false：synonyms、translation_en-de、translation_en-es、translation_en-fr。
- 最终 null：taxonomy_animal。其最后 OracleResponse 的解析可复现 JSONDecodeError，无法将该 null 简单当作模型还未学会或 judge 确信不等价。
- sentence_similarity、word_in_context 等存在不生成新候选的 NoCounterexample 终止记录，需避免把 epoch 条数当作生成调用数。

失败题仍多是“合理泛化指令”与“数据集精确答案”的冲突：德语 season 参考 Staffel，judge 推测指令会输出 Jahreszeit；法语 film 参考 pellicule，指令可能输出 film；synonyms 的 account 参考 accounting，judge 推测 record。candidate_output 是 judge 推测，不是实际执行出来的输出。

上次小规模 antonyms 被连续否决，本轮第一轮即被 judge 接受；初始候选和 oracle 输出不同，不能据此宣称任务已稳定解决。Std 从未调用同一等价判定，因此无法做 std vs CE 的 0/24 vs 19/24 比较。合理的表述是“CE 有 19/24 被本轮 heuristic oracle 接受”。

## 7. 结论与建议的优先级

1. **优先修复并隔离列表可变输入。** 在 reference 和 candidate 执行边界复制输入，避免改变 train/eval/pool 及已记录的 CE；至少重跑 c067，再复核允许原地操作的题目。当前 c067 成绩应标记为数据污染，不用于方法胜负。
2. **统一有效候选保留与终止汇总。** 明确记录 last_attempt、last_valid、best_train_fit、终止原因；不要将测试集最高分直接选作输出，也不要让终止标记丢失最后有效候选的指标。
3. **修复 prompt 与 validator 的契约。** SCAN 有大量 while/import/方法调用/参数名不兼容，需要区分语义失败和程序未获准执行，避免重复生成同类无效程序。
4. **区分真实 CE、重复 CE 和 fallback 普通数据。** 现在能够确认一部分真实修复，但大部分列表追加条目不是错误样本；统一计作 CE 会误读机制。
5. **Instruction Induction 增加实际执行评测和稳健 JSON 解析。** 语义 judge 接受率单列，不冒充可执行的精确准确率。
6. **在上述问题解决后比较匹配预算的多 run。** 当前两边初始 N 不同，列表 std 最多 3 次生成、CE 通常 8 次，且只有一个 run。可以把 c164、SCAN length/addprim_jump 作为成功轨迹案例，同时将 c211 作为“有限测试满分仍有反例”的案例。

本次未调用 LLM、未安装依赖、未重跑 benchmark、未修改模型/runner/数据集或原始日志。离线使用已有受限执行器检查 previous 对 CE 的预测，并用复制输入复核记录标签。
